# A｜校园交流与找同伴

负责人为 [`jack-wjy`](https://github.com/jack-wjy)。本文梳理五条功能故事，覆盖结伴发起者、筛选寻找者与申请加入的同学，串起「发布组队需求 → 多维筛选发现 → 申请加入与隐私隔离 → 发起者审批与满员锁定 → 主动结帖与状态管理」的完整闭环。

全篇统一帖子状态枚举：**`招募中`**、**`已成队`**（达到目标人数上限）、**`已结束`**（到达截止时间或发起者手动结帖）。

## 调研观察与脱敏访谈摘要

整理日期为 2026-11-24（2026-11-25 依据审核意见补充渠道、时间范围与细节）。

### OBS-A01 跨校区与课程群找队友信息沉底观察

- **观察渠道与时间**：2026 年 11 月，观察同济大学四平路/嘉定跨校区公共数学课程 QQ 交流群（约 400 人）。
- **观察经过**：有同学在群内发送文字消息，希望寻找同授课教师的期末自习与答疑同伴；约半小时内，该消息被上百条作业截图、日常闲聊及表情包刷屏淹没，且原消息未写明校区、期望自习时间段与所需人数，导致有意向的同学需反复翻找并私聊核对基础条件。
- **对应需求**：支持 A-01 结构化发布招募（分类、校区、目标人数、截止时间），以及 A-02 按校区、分类和有效状态的组合筛选。

### INT-A01 期末自习找同伴的隐私顾虑

- **受访者与时间**：四平路校区某工科专业大二学生（匿名），2026 年 11 月中旬。
- **经过与结果**：受访者希望在期末周寻找同课程同学在图书馆固定自习，但在课程大群或朋友圈公开招募时，该受访者明确顾虑直接公开个人微信号或手机号会引来无关人员或营销号加好友打扰，同时也不希望自己的申请留言被群里无关同学看到。
- **对应需求**：支持 A-03 将申请附言与联系方式限制在授权范围内，未获发起者同意前不向他人及接口公开，且不强制暴露微信号即可通过站内方式继续组队。

### INT-A02 兴趣运动约球满员与状态失效

- **受访者与时间**：嘉定校区某工科专业大三学生（匿名），2026 年 11 月中旬。
- **经过与结果**：受访者在羽毛球交流群发布周末 4 人双打约球消息。线下与私聊凑齐 4 人后，由于群消息无法修改状态或标记结帖，随后两天仍有同学继续发消息询问是否还有空位；同时存在多名同学同时询问最后 1 个名额导致的沟通冲突。
- **对应需求**：支持 A-04 在名额达到上限时自动锁定为「已成队」并失效多余待审批申请，以及 A-05 由发起者主动结帖停止招募。

## 用户故事与可检验验收标准

本模块 5 条功能故事均遵循三段式（作为/我想/以便）与可重复检验的 `Given / When / Then` 验收标准，并已同步至 GitHub Issue [#18](https://github.com/aserssi/se-design-campus-circle/issues/18)–[#22](https://github.com/aserssi/se-design-campus-circle/issues/22)。

### A-01｜学生发布寻找自习或活动同伴的招募帖（对应 Issue [#18](https://github.com/aserssi/se-design-campus-circle/issues/18)）

作为希望寻找学习或课外活动伙伴的在校学生，我想发布结构化的结伴需求（包含分类、主题描述、校区、目标人数和截止时间），以便快速吸引契合目标的同学加入，并在到期后自动停止接收申请。

- **正常发布（默认与自定义截止时间）**：
  - **Given**：我已登录校圈账号，进入“找同伴”发布页面，表单默认预填截止时间为当前日期起第 7 天 23:59。
  - **When**：我选择分类“自习/备考”、填写主题与描述、选择校区“四平路校区”、设置目标总人数为 `3`（可保留默认截止时间或修改为未来某一有效时间，如 `2026-12-01 20:00`）并提交。
  - **Then**：系统生成一条状态为「招募中」的帖子，详情页展示发起者默认占 1 席（当前进度 `1/3`）以及所设定的截止时间；到达该截止时间后，帖子自动停止接受新申请，状态流转为「已结束」。
- **人数下限与必填校验**：
  - **Given**：我已登录并处于发布页面。
  - **When**：我未填写主题描述，或将目标总人数设为 `1`（或 `0`、负数）后点击提交。
  - **Then**：系统拒绝创建帖子并提示“请填写完整主题，且目标总人数至少为 2 人”。
- **自动到期时待审批申请处理**：
  - **Given**：我发布的「招募中」帖子已到达设定的截止时间，且队列中仍有账号 B 提交的一条「待审批」申请。
  - **When**：系统到达截止时间并触发自动结束；随后发起者尝试在管理页点击同意账号 B，同时账号 B 打开自己的“我的申请”记录。
  - **Then**：帖子自动流转为「已结束」并停止接受新申请；账号 B 原「待审批」申请自动变为「已关闭（招募已到期）」；发起者点击批准时系统拒绝操作并提示“招募已到期”；账号 B 在个人申请记录中看到该申请状态为「已关闭（招募已到期）」。

调研证据：[OBS-A01 跨校区与课程群找队友信息沉底观察](#obs-a01-跨校区与课程群找队友信息沉底观察) · [INT-A01 期末自习找同伴的隐私顾虑](#int-a01-期末自习找同伴的隐私顾虑)

### A-02｜学生按校区、分类与状态筛选有效的同伴招募（对应 Issue [#19](https://github.com/aserssi/se-design-campus-circle/issues/19)）

作为正在寻找队伍的在校学生，我想按校区、活动分类及招募状态进行组合筛选，自动过滤已成队或已到期的帖子，以便快速找到当前仍有空位且适合自己的队伍。

- **三项组合筛选与到期过滤**：
  - **Given**：在正常负载环境下，找同伴列表库中存在 4 条帖子：帖子 1（嘉定校区、课程大作业、招募中、未到期）、帖子 2（嘉定校区、课程大作业、招募中但已过截止时间）、帖子 3（嘉定校区、课程大作业、已成队）、帖子 4（四平路校区、课程大作业、招募中、未到期）。
  - **When**：我在筛选栏选择校区“嘉定校区”、分类“课程大作业”，并勾选“仅看招募中”后点击筛选。
  - **Then**：正常负载下，从点击筛选起 1 秒内，列表首屏仅渲染展示帖子 1（并显示剩余名额），自动排除已到期的帖子 2、已成队的帖子 3 和非目标校区的帖子 4。
- **无匹配空状态**：
  - **Given**：正常负载下，当前库中没有同时满足“嘉定校区 + 兴趣运动 + 招募中（未到期）”的帖子。
  - **When**：我提交该三项组合筛选条件。
  - **Then**：正常负载下，1 秒内首屏展示空态提示“暂无相关招募，你可以发起一个”，不展示过期或无关帖子。

调研证据：[OBS-A01 跨校区与课程群找队友信息沉底观察](#obs-a01-跨校区与课程群找队友信息沉底观察)

### A-03｜申请结伴时保护申请附言与个人联系方式隐私（对应 Issue [#20](https://github.com/aserssi/se-design-campus-circle/issues/20)）

作为有意加入队伍的在校学生，我想向发起者提交仅双方可见的申请附言，并自主独立决定入队后是否分享个人联系方式，以便发起者评估匹配度，同时防止未授权用户获取我的附言或微信号/手机号。

- **提交申请与隐私隔离（三视角核对）**：
  - **Given**：账号 B 打开账号 A 发布的未到期「招募中」帖子，此前未申请过该帖；双方对各自联系方式的分享选择相互独立。
  - **When**：账号 B 点击“申请加入”，填写附言“高数已复习两轮，周三周五晚有空”，选择“暂不提供微信号，入队后使用站内联系”（或勾选“入队后向发起者分享微信号”并填写），点击提交。
  - **Then**：系统提示申请已提交，原帖对账号 B 显示“已申请，待处理”。分别用三个账号核对界面与接口返回：
    1. **发起者账号 A**：在申请管理列表中看到该申请及附言；在审批通过前，看不到账号 B 的微信号/手机号。
    2. **申请人账号 B**：可看到自己的申请记录与状态。
    3. **无关学生账号 C**：在原帖详情、公共评论区及后台接口返回体中，均获取不到账号 B 的申请附言与任何联系方式。
- **不留微信号可继续组队与防重复提交**：
  - **Given**：账号 B 未填微信号并已提交一条「待审批」申请。
  - **When**：账号 B 再次点击提交申请；以及随后发起者 A 同意账号 B 入队。
  - **Then**：重复提交请求被系统拦截并提示“已提交过申请”，后台不新增第二条记录，也不向发起者重复发送通知；账号 A 同意后，账号 B 正常入队（不因未提供微信号受阻），双方可通过校圈站内消息继续沟通。

调研证据：[INT-A01 期末自习找同伴的隐私顾虑](#int-a01-期末自习找同伴的隐私顾虑)

### A-04｜发起者审批申请、授权分享联系方式及满员自动锁定（对应 Issue [#21](https://github.com/aserssi/se-design-campus-circle/issues/21)）

作为结伴发起者，我想在管理页审核待处理申请，同意后按双方授权展示联系方式并在满员时自动锁定招募，以便避免最后名额被多人重复占用并建立组队联系。

- **顺序审批最后 1 席与满员锁定**：
  - **Given**：发起者 A 的招募帖目标总人数为 3 人，当前进度为 `2/3`（状态「招募中」），队列中有账号 C 与账号 D 两条「待审批」申请。
  - **When**：发起者 A 在管理页先点击同意账号 C 加入。
  - **Then**：当前人数更新为 `3/3`，账号 C 成功入队，状态由「招募中」自动变为「已成队」，前台关闭新申请入口；账号 D 的待审批申请自动变更为「已失效（名额已满）」，无法再被同意入队。
- **并发审批最后 1 席**：
  - **Given**：招募帖目标总人数为 3 人，当前进度为 `2/3`，队列中同时有账号 C 与账号 D 两条「待审批」申请。
  - **When**：发起者 A 对最后 1 席几乎同时并发触发“同意 C”与“同意 D”两个请求。
  - **Then**：系统串行锁定剩余名额，最终**恰好一人成功入队**（总人数严格保持 `3/3`、状态变为「已成队」），另一人的申请自动变为「已失效（名额已满）」，且后处理的审批请求返回名额已满提示，不会超员。
- **单向独立的联系方式授权展示**：
  - **Given**：发起者 A 与申请人各自独立设置是否向已入队同伴分享联系方式；账号 C 在申请时勾选“同意分享微信号”，发起者 A 设置为“不公开/未同意分享微信号”，账号 D 为未获准申请人。
  - **When**：发起者 A 同意账号 C 入队后，分别用发起者 A、获准申请人 C 和未获准申请人 D 三个账号查看详情及接口返回。
  - **Then**：发起者 A 可看到账号 C 分享的微信号；账号 C 看不到发起者 A 的微信号（双方可通过校圈站内消息联系）；未获准申请人 D 看不到发起者 A 与账号 C 任何一方的联系方式。
- **非发起者越权审批拦截**：
  - **Given**：普通账号 E 打开账号 A 发布的招募帖详情或尝试访问审批接口。
  - **When**：账号 E 尝试查看申请列表或提交“同意申请”请求。
  - **Then**：系统返回 403 拒绝访问，不返回申请名单、附言及联系方式，帖子人数与申请状态均不发生变更。

调研证据：[INT-A02 兴趣运动约球满员与状态失效](#int-a02-兴趣运动约球满员与状态失效) · [INT-A01 期末自习找同伴的隐私顾虑](#int-a01-期末自习找同伴的隐私顾虑)

### A-05｜发起者主动关闭招募帖与未审批申请处理（对应 Issue [#22](https://github.com/aserssi/se-design-campus-circle/issues/22)）

作为结伴发起者，我想在线下已凑齐人员或计划变动时主动结束招募，以便停止接收新申请并告知已申请同学招募结束。

- **主动结束招募（支持招募中与已成队）**：
  - **Given**：由我发起的帖子当前处于「招募中」（尚有 1 条来自账号 C 的「待审批」申请）或处于「已成队」状态。
  - **When**：我点击“结束招募”，填写关闭原因（如“线下已凑齐”或“因考试改期活动取消”）并确认。
  - **Then**：帖子状态流转为「已结束」，详情展示关闭原因与关闭时间；系统关闭新申请入口；原队列中尚未审批的账号 C 申请自动变为「已关闭（招募已结束）」。若原已成队且未取消活动，已入队成员的既有站内联系保留。
- **非发起者越权结帖拦截**：
  - **Given**：普通账号 D 打开他人发起的「招募中」或「已成队」帖子。
  - **When**：账号 D 尝试提交结束招募请求。
  - **Then**：系统返回 403 权限拒绝，帖子原状态、申请队列均保持不变。

调研证据：[INT-A02 兴趣运动约球满员与状态失效](#int-a02-兴趣运动约球满员与状态失效)

## 向任务 D（社区管理与非功能需求）交接清单

为确保全组接口链路清晰、验收口径一致，A 模块向 D 模块交接以下非功能场景：

| 维度 | 链路与交接场景说明 | 建议验收口径（与 D 模块对齐） |
| :--- | :--- | :--- |
| **安全：隐私与授权边界** | 申请附言仅发起者与申请人本人可见；联系方式仅双方授权且审批通过后对当事人可见，不填微信号仍支持站内联系；普通用户禁止越权查看他人申请列表或修改招募状态。 | 覆盖发起者、获准申请人、无关学生三类视角验收；未授权账号读取返回 403，接口返回体脱敏或不含私密字段（对应加强 `D-04` 权限边界设计）。 |
| **性能：列表筛选基准** | `D-03` 验收的是 C 模块「经验检索」，A 的「找同伴多维筛选列表」是独立接口。若沿用 `100 QPS、3 分钟`，本项明确作为 **A 接口的候选压测基准**；A-02 中“点击筛选到首屏 1 秒”是在**正常负载**下验收的前端目标。 | 候选基准：稳态 **100 QPS 持续运行 3 分钟**，至少 95% 请求在 **1.5 秒**内返回有效结果，失败率 < 0.1%（参考 `D-03` 基准形态独立评估）。 |
| **可用性：推送中断降级** | 当外部通知推送依赖不可用时，组队申请提交与站内查收必须不受影响，恢复后补发积压通知且不重复。 | 申请提交成功 **3 秒内**站内申请列表与站内通知均可见；推送服务恢复后 **30 秒内**接收积压通知一次且不重复（与 `D-05` 验收口径完全一致）。 |
