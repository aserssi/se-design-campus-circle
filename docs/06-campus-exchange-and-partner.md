# A｜校园交流与找同伴

负责人为 [`jack-wjy`](https://github.com/jack-wjy)。本文梳理五条功能故事，覆盖结伴发起者、寻找队伍的同学以及提交申请的成员，串起「发布组队需求 → 多维筛选发现 → 申请加入意向 → 发起者审批与满员锁定 → 主动结帖与状态管理」的完整业务闭环。

---

## 真实校园场景与经验观察

查阅与整理日期为 2026-11-24。结合在校同学日常学习生活中的真实组队痛点（如期末自习备考、课外竞赛、兴趣运动等），梳理出现有渠道的缺陷与设计依据。

### OBS-A01 跨校区/跨学院寻找队伍痛点
- **现状观察**：同济大学四平路与嘉定双校区选课与竞赛群中，寻找大创、数模或课程大作业队友的信息极易被日常闲聊刷屏冲水。
- **现存问题**：信息缺乏结构化字段（如缺少专业方向、明确目标、所需技能、目标人数），导致沟通成本极高，反复私聊询问后才发现校区不合或目标不一致。
- **对应支持**：支持 A-01 结构化发布结伴需求（分类、校区、截止时间与人数上限），以及 A-02 的多维标签过滤。

### INT-A01 期末高数与专业课自习找同伴
- **经历还原**：受访学生希望在期末周寻找“同一老师/同一门课”的同学在图书馆固定自习、互相答疑督促。在朋友圈或大群发布招募后，常受到无关好友评论打扰，且容易泄露个人作息习惯等隐私。
- **现存问题**：缺乏只面向结伴目的的轻量沟通机制，学生普遍排斥在公开大群直接展示个人微信号或手机号。
- **对应支持**：支持 A-03 提交加入意向时对联系方式进行隐私保护与隔离，未获发起者确认前不向公众暴露个人敏感联络信息。

### INT-A02 兴趣运动结伴满员与状态失效
- **经历还原**：受访学生在羽毛球群发起周末双打约球（需要 4 人）。在线下或微信私聊满员后，原群消息无法撤回或修改状态，导致后续仍有同学不断发起私聊询问。
- **现存问题**：招募缺乏状态机生命周期管理（招募中、已满员、已结束），缺少满员自动闭锁与发起者主动结帖机制。
- **对应支持**：支持 A-04 审批通过后满员自动锁定，以及 A-05 发起者手动结帖。

## 用户故事与可检验验收标准

本模块 5 条功能故事均严格遵循三段式（作为/我想/以便）与可量化检验的 `Given / When / Then` 验收标准，并已在 GitHub Issue 中建单入库。

### A-01｜学生发布寻找自习或活动同伴的招募帖（对应 Issue [#18](https://github.com/aserssi/se-design-campus-circle/issues/18)）

#### 用户故事
作为 **希望寻找学习或课外活动伙伴的在校学生**，  
我想 **发布结构化的结伴需求（包含活动类型、校区、时间与所需人数）**，  
以便 **快速吸引契合目标的同学加入，避免在群聊中反复核对基础信息**。

#### 验收标准
- **Given**：我已登录校圈账号，进入“找同伴”发布界面；
- **When**：我选择分类（如“自习/备考”）、填写活动主题与详细描述、选择所在校区（如“四平路校区”）、设置目标总人数（如 3 人）并点击提交；
- **Then**：系统在 1 秒内创建帖子，状态标记为「招募中」，详情页展示发起者已占用 1 席（当前进度：`1/3`），并展示截止时间；
- **异常拦截**：若未填写活动主题描述，或目标总人数未设定（或小于 1），点击提交时界面弹出红字提示“请完善主题并设置有效人数”，本次操作不创建帖子。

#### 调研证据
- [OBS-A01 跨校区/跨学院寻找队伍痛点](#obs-a01-跨校区跨学院寻找队伍痛点)
- [INT-A01 期末高数与专业课自习找同伴](#int-a01-期末高数与专业课自习找同伴)

### A-02｜学生按校区与主题筛选当前的有效招募（对应 Issue [#19](https://github.com/aserssi/se-design-campus-circle/issues/19)）

#### 用户故事
作为 **正在寻找队伍的在校学生**，  
我想 **按校区和分类快速筛选同伴帖，并过滤掉已失效或满员的帖子**，  
以便 **在 2 秒内找到当前有效且适合自己的队伍，避免无效沟通**。

#### 验收标准
- **Given**：我处于找同伴列表页，库中存在跨校区（四平、嘉定）以及处于不同状态（招募中、已满员、已结束）的历史帖子；
- **When**：我在筛选栏选择校区为“嘉定校区”、分类勾选“课程大作业”、并勾选“仅看招募中”选项；
- **Then**：系统在 1 秒内刷新列表，仅展示符合上述条件的招募卡片；卡片清晰展示“剩余名额”，不展示已满员或已结帖的内容。若无匹配项，则展示空状态占位提示“暂无相关招募，你可以发起一个”。

#### 调研证据
- [OBS-A01 跨校区/跨学院寻找队伍痛点](#obs-a01-跨校区跨学院寻找队伍痛点)

### A-03｜申请结伴时保护个人微信/手机号隐私（对应 Issue [#20](https://github.com/aserssi/se-design-campus-circle/issues/20)）

#### 用户故事
作为 **有意加入队伍的在校学生**，  
我想 **向发起者提交个人说明与加入意向**，  
以便 **发起者评估匹配度，同时不在公共留言区暴露个人微信或手机号，防止无关骚扰**。

#### 验收标准
- **Given**：我作为普通登录学生（账号 B），打开另一位同学（账号 A）发布的处于「招募中」的同伴帖，且账号 B 此前未申请过该帖；
- **When**：我点击“申请加入”，在弹出表单中输入申请附言（如“我擅长数据分析，高数期中90+”）并提交；
- **Then**：系统提示“申请已提交，请等待发起者确认”；发起者后台收到该申请条目，但帖子的公共讨论区域不展示我的微信号、手机号或学号；该帖子对账号 B 状态更新为“已申请”，禁用重复点击。

#### 调研证据
- [INT-A01 期末高数与专业课自习找同伴](#int-a01-期末高数与专业课自习找同伴)

### A-04｜发起者确认入队且满员后自动锁定招募（对应 Issue [#21](https://github.com/aserssi/se-design-campus-circle/issues/21)）

#### 用户故事
作为 **结伴发起者**，  
我想 **在管理页审核收到的申请，并在达到目标人数后由系统自动满员锁定**，  
以便 **锁定队友、建立联系，同时不再接收多余申请打扰**。

#### 验收标准
- **场景一（正常审批与满员闭锁）**：
  - **Given**：我发起的组队帖目标人数为 2 人，当前进度为 `1/2`，收到账号 C 的加入申请；
  - **When**：我在申请列表中点击“同意加入”；
  - **Then**：队伍人数自动更新为 `2/2`，帖子状态由「招募中」流转为「已成队」；前台自动关闭该帖的“申请加入”入口；系统向双方安全展示约定的联络方式（微信号/手机号）。
- **场景二（权限拦截）**：
  - **Given**：普通用户 D 打开非自己发起的结伴帖详情；
  - **When**：用户 D 尝试通过前端控制台或直接调用 API 接口发起审核操作；
  - **Then**：系统返回 403 权限拒绝，数据不发生变更，不泄露其他申请人的信息。

#### 调研证据
- [INT-A02 兴趣运动结伴满员与状态失效](#int-a02-兴趣运动结伴满员与状态失效)

### A-05｜发起者手动关闭招募帖与状态更新（对应 Issue [#22](https://github.com/aserssi/se-design-campus-circle/issues/22)）

#### 用户故事
作为 **结伴发起者**，  
我想 **在线下已找到同伴或计划变更时随时主动结帖**，  
以便 **告知其他同学该活动已结束，不再接收无效申请**。

#### 验收标准
- **Given**：由我发起的帖子处于「招募中」或「已成队」状态，线下已有队友加入；
- **When**：我在该帖点击“结束招募”，并填写说明“线下已组满”；
- **Then**：帖子状态更新为「已结束」，详情展示结束说明与时间戳，列表将其移至历史归档区，关闭任何新申请提交。
- **权限约束**：非发起者点击结束招募时，系统提示“无权修改他人招募状态”，保持原状态不变。

#### 调研证据
- [INT-A02 兴趣运动结伴满员与状态失效](#int-a02-兴趣运动结伴满员与状态失效)

## 向任务 D（社区管理与非功能需求）交接清单

根据组内协作约定，A 模块将调研中涉及的权限安全、隐私保护、高并发及服务中断场景向负责 D 模块的同学进行规范交接：

| 维度 | 交接场景与具体需求 | 建议验收量化指标 |
| :--- | :--- | :--- |
| **安全：隐私保护** | 结伴未正式确认前，普通学生的个人联系方式（手机号、微信号）严格进行脱敏掩码，禁止在公有 API 接口返回明文数据。 | API 响应中联系方式脱敏率为 100%，防止爬虫抓取。 |
| **安全：防水平越权** | 申请审核、结帖操作必须进行严格的 Session/JWT 身份鉴权，杜绝攻击者通过遍历 `post_id` 篡改他人帖子的招募状态。 | 跨用户越权请求拦截率 100%，系统统一返回 403 Forbidden。 |
| **性能：选课与期末检索并发** | 期末备考季与开学找队友高峰期，多标签组合检索列表接口需要承受学生瞬时刷新的并发压力。 | 基准档位：**持续 100 QPS 施压 2 分钟**，接口响应时延 P95 ≤ 800ms，系统错误率 < 0.1%。 |
| **可用性：即时通知降级** | 当组队申请的即时通知服务（如 WebSocket / 第三方推送）网络中断或故障时，核心数据不能丢失。 | 系统在 3 秒内平滑降级为站内轮询通知，故障恢复后 30 秒内补偿积压通知。 |
