## 3. 交付 D 的检索性能场景与压测候选假设（待 D 团队确认）

为了满足期末周和选课周学生集中查询的需求，C 模块提出以下高并发检索场景作为**候选压测假设**，由 D 团队根据系统部署架构与测试环境最终确认并纳入非功能故事：

### 3.1 业务峰值场景设定
* **典型情境**：期末考试前 3 天冲刺阶段，或全校选课系统开放初期的前 10 分钟。
* **业务动作**：用户同时发起带关键词过滤、课程代码筛选（如 `#MATH1001`）与时效性排序的多条件复杂检索。

### 3.2 压测口径与候选指标建议（供 D 选定）

1. **并发负载换算与测试档位建议（建议候选档位：50 / 100 / 200 VU）**：
   * *基础在校规模*：全校在校生约 20,000 人，高峰期活跃在线用户估算为 5%~10%（约 1,000~2,000 人）；
   * *平稳检索阶段（分钟级背景负载）*：若 1,000 名在线用户中约 10%~20% 在 1 分钟内分散发起 1 次检索，系统产生约 100~200 次请求/分钟，平均吞吐量仅为 `1.7 ~ 3.3 QPS`（属于系统日常基线负载）；
   * *瞬时突增峰值（秒级冲刺窗口）*：在选课系统开放或考试周突击冲刺的瞬时冲击时间窗（前 5~10 秒内），假设有 50 ~ 200 名并发虚拟用户（Virtual Users, VU）几乎同时提交多维检索请求，或每个用户在 5 秒内连续点击筛选/翻页（每人每秒发出 1 次请求），此时系统后端在瞬时承受 **50 ~ 200 QPS（次/秒）** 的吞吐压力；
   * *压测候选测试档位*：
     - **轻载档位**：50 并发用户（VU）持续以 50 QPS 施压；
     - **基准推荐档位**：100 并发用户（VU）持续以 100 QPS 施压（对应常规期末高峰）；
     - **极限挑战档位**：200 并发用户（VU）持续以 200 QPS 施压（对应选课瞬时秒级并发冲击）。
2. **压测时长建议（建议：稳态 3~5 分钟）**：
   * 压测脚本宜设置：升温爬坡（Ramp-up）1 分钟，保持目标并发稳态运行 3 分钟，以检测数据库连接池耗尽、垃圾回收（GC）引起的延迟抖动。
3. **响应时间阈值（候选建议）**：
   * **P95 响应时间 ≤ 1.5 秒**（即 95% 的检索 API 请求在 1.5 秒内完成查询并返回 JSON）；
   * 前端首屏在 **2.0 秒内** 完成渲染，避免学生因等待而反复刷新。
4. **错误率统计口径（建议阈值：< 0.1%）**：
   * *定义口径*：`错误率 = (HTTP 5xx 服务端错误响应数 + 超时未返回数) / 发出总请求数 * 100%`。
   * 在稳态压测期内不得发生服务进程崩溃重启。

## 4. 建议 D 直接采用的【性能】非功能故事模板（草案）

D 同学在编写 3 条非功能故事中的性能故事时，可基于上述候选假设直接细化：

### Issue 标题：`[D][性能] 选课与考试周高峰期支持多用户秒级检索`
* **Labels**: `story`, `non-functional`, `performance`
* **用户故事**：
  > 作为 **在校学生（期末冲刺与选课查阅者）**，  
  > 我想 **在选课与考前高峰期多用户同时检索历史经验时，系统仍能在 2 秒内极速返回结果**，  
  > 以便 **快速获得复习指导与避坑指南，不因系统卡顿延误决策**。
* **验收标准**：
  * **Given**：系统经验库导入 5,000+ 条模拟历史经验，性能测试客户端配置为 100 个并发用户（持续以 100 QPS 施压）并在稳态 3 分钟内持续发起多维复合检索；
  * **When**：执行压测脚本并在服务端监控响应时间与错误数；
  * **Then**：统计报表显示 95%（P95）的请求在 1.5 秒内成功返回 HTTP 200，且计算所得错误率（5xx及超时请求数 / 总请求数）低于 0.1%。
