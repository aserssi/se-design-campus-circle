如果 D 同学直接编写“响应时间小于 2 秒”或“支持 200 并发”，在评审时会因缺乏真实数据支撑被质疑为“凭空捏造”。为此，C 模块完成真实校园论坛实测（详见 [evidence.md](evidence.md)），将测得的基准耗时与业务高峰场景整理为本清单，直接作为 D 编写**性能非功能用户故事**的依据。

## 2. 现有渠道实测基准耗时数据（Baseline）

在同济大学学生社区论坛（YourTJ Forum）及群聊实测中，不同检索任务的人工操作耗时统计如下：

| 测试任务与场景 | 对应证据 | 现有渠道操作步骤与现实瓶颈 | 测得人工基准耗时 |
| :--- | :--- | :--- | :--- |
| **任务 1：课程期中补救与备考指南检索** | OBS-001 | 用户在无标签、无课程代码的板块中翻阅帖子列表，逐条查看回帖提取有用建议。 | **73.5 秒**（70~82秒波动） |
| **任务 2：大数据专业培养方案与选课经验辨析** | OBS-002 | 用户需阅读 11 条长回帖，并手动核实不同届别的政策差异，排除过期信息。 | **145 秒** |
| **任务 3：突发实验补选流程紧急查询** | OBS-003 | 论坛发帖 24 小时无人回应，群聊搜索关键词产生上百条闲聊干扰，无法自助解决。 | **> 180 秒**（且未解决） |

**瓶颈分析**：人工搜索耗时均在 1~3 分钟，且随信息量增加急剧恶化，极易在选课周、期末考试周造成严重的信息焦虑。

## 3. 交付 D 的高并发性能场景设定（Target Scenario）

### 业务场景描述：期末周 / 选课周高并发经验检索高峰
* **峰值情境**：在期末考试前 3 天或开学前选课开放后的前 10 分钟，全校可能有上千名学生同时涌入系统检索往年复习笔记、实验报告避坑指南与选课评分。
* **业务负载估算**：设定典型高负载为 **200 个并发查询请求** 同时发起（包含全文检索、多标签组合筛选及按时效性排序）。
* **用户体验容忍底线**：
  * API 检索响应：P95 响应耗时不超过 **1.5 秒**；
  * 前端首屏渲染：前 10 条高相关度经验卡片在 **2.0 秒内** 完成渲染，避免白屏；
  * 错误率容忍：在 200 并发压力下，HTTP 5xx 错误率低于 **0.1%**。

## 4. 建议 D 直接采用的性能非功能故事（草案）

D 同学在编写 3 条非功能故事中的**【性能】**故事时，可直接参考以下格式录入 Issue：

### Issue 标题：`[D][性能] 选课与考试周高峰期支持 200 并发秒级检索`
* **标签**：`story`, `non-functional`, `performance`
* **用户故事**：
  > 作为 **在校学生（期末备考或选课查找攻略者）**，  
  > 我想 **在期末周与选课周高峰期多用户同时查询时，系统依然在 2 秒内极速返回历史经验列表**，  
  > 以便 **在紧急选课或考前复习时快速获得指南，不受系统卡顿或崩溃影响**。
* **验收标准**：
  * **Given**：系统经验库中已有 10,000+ 条历史经验与问答数据，且模拟有 200 个客户端在 1 秒内同时提交多维复合检索请求；
  * **When**：执行高并发性能压测脚本；
  * **Then**：95%（P95）的检索请求在 1.5 秒内返回 HTTP 200 及结构化 JSON 结果，整个系统首屏渲染完成耗时不超过 2.0 秒，压测期间服务器无宕机且错误率低于 0.1%。
* **调研证据链接**：
  * 追溯到 C 模块交付的实测数据：`docs/task-c/handover-to-d.md` 及 `docs/task-c/evidence.md#2-现有渠道实测记录obs`
