## 3. 交付 D 的检索性能场景与压测候选假设（待 D 团队确认）

为了满足期末周和选课周学生集中查询的需求，C 模块提出以下高并发检索场景作为**候选压测假设**，由 D 团队根据系统部署架构与测试环境最终确认并纳入非功能故事：

### 3.1 业务峰值场景设定
* **典型情境**：期末考试前 3 天冲刺阶段，或全校选课系统开放初期的前 10 分钟。
* **业务动作**：用户同时发起带关键词过滤、课程代码筛选（如 `#MATH1001`）与时效性排序的多条件复杂检索。

### 3.2 压测模型与候选指标定义（供 D 选定）

为了避免混淆“用户瞬时各点一次”与“持续恒定施压”，本交接将压力测试清晰拆分为**两套独立负载模型**：

#### 模型一：持续到达率基准压测模型（核心验收指标，固定以请求到达率 QPS 验收）
* **验收口径**：采用**恒定请求到达率（Arrival Rate / QPS）**核对压测结果，模拟考试周与选课周高峰期高频稳定的多维复合检索流。
* **测试档位设计**：
  * **基准推荐档位（Baseline Target，系统合格线）**：
    * **请求到达率**：恒定 **100 QPS（次/秒）**；
    * **压测时长与总量**：升温（Ramp-up）1 分钟，**稳态持续施压 3 分钟**（稳态总请求量为 18,000 次）；
    * **验收合格判据**：95%（P95）检索请求响应耗时 ≤ **1.5 秒**，前端首屏渲染 ≤ **2.0 秒**，服务端错误率 < **0.1%**。
  * **极限挑战档位（Stress / Overload Challenge，过载弹性评估）**：
    * **请求到达率**：恒定 **200 QPS（次/秒）**；
    * **压测时长与总量**：稳态持续施压 3 分钟（稳态总请求量为 36,000 次）；
    * **目的**：测试系统在极端并发负荷下的连接池上限与慢查询瓶颈。
* **错误率统计口径**：
  * `错误率 = (HTTP 5xx 服务端错误响应数 + 超时未返回数) / 发出总请求数 * 100%`，稳态压测期内不得发生服务进程崩溃或连接池耗尽死锁。

#### 模型二：瞬时突发脉冲测试模型（健壮性辅助验证，以并发虚拟用户数 VU 验收）
* **验收口径**：采用**并发虚拟用户数（Virtual Users, VU）的一次性瞬时脉冲冲击**。
* **测试情境**：模拟选课系统开放或考试成绩公布瞬间（**1~2 秒** 窄时间窗内），全校学生同时点击“查询”按钮。
* **负载规模与动作**：
  * 客户端瞬间激发 **100 ~ 200 个并发连接（VU）**，每位虚拟用户仅发起 1 次复杂检索请求（瞬时突发请求总量 100~200 次）；
  * 冲击时间 ≤ 2 秒；
* **验收合格判据**：服务端连接池不崩溃、无 502/504 网关超时错误，所有排队请求在 3 秒内平稳消化完毕，服务在冲击结束后 5 秒内恢复至常规基线响应水平。

## 4. 建议 D 直接采用的【性能】非功能故事模板（草案）

D 同学在编写 3 条非功能故事中的性能故事时，可基于基准压测模型（持续 100 QPS 稳态 3 分钟）直接录入 Issue：

### Issue 标题：`[D][性能] 选课与考试周高峰期支持 100 QPS 持续稳定检索`
* **Labels**: `story`, `non-functional`, `performance`
* **用户故事**：
  > 作为 **在校学生（期末冲刺与选课查阅者）**，  
  > 我想 **在选课与考前高峰期多用户密集检索历史经验时，系统仍能在 2 秒内极速返回结果**，  
  > 以便 **快速获得复习指导与避坑指南，不因系统卡顿延误决策**。
* **验收标准**：
  * **Given**：系统经验库导入 5,000+ 条模拟历史经验，压测脚本配置为以恒定 100 QPS 到达率持续施压稳态 3 分钟（总计 18,000 次多维复合检索请求）；
  * **When**：执行压测脚本并在服务端监控响应时间与错误数；
  * **Then**：统计报表显示 95%（P95）的请求在 1.5 秒内成功返回 HTTP 200，首屏渲染耗时 ≤ 2.0 秒，且计算所得错误率（5xx及超时请求数 / 总请求数）低于 0.1%（极限 200 QPS 作为候选过载挑战档位）。
